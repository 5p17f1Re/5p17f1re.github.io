# Журнал решений

Это каноническая история технических и визуальных решений, принятых для сайта.
Запись фиксирует не только результат, но и причину выбора. Новые записи добавляются
до коммита соответствующего изменения; если решение меняет ранее принятое поведение,
в новой записи указывается, что именно заменено и почему.

## 2026-08-21 — первый реальный publish E2E и границы текущего v0

### Решение

- Считать базовый сценарий публикации подтверждённым: реальный batch из четырёх
  фотографий прошёл путь Telegram → Worker → R2/D1 → GitHub Actions → один
  publication commit → GitHub Pages → callback Worker со статусом `published`.
- Считать GitHub Pages публичным слоем, а R2 — временным приватным staging. R2
  не становится архивом или обязательным источником выдачи фотографий в браузер.
- Сохранить ручной запуск workflow как текущий операционный режим. Среду cron не
  включать, пока отдельно не пройдены снятие публикации, RAW/GPS-проверки,
  failed/empty/retry batch и проверка длительной паузы.
- Оставить управление очередью текстовыми командами. Формат
  `/1 2 5 cancel` — пример выбора номеров; кнопочный интерфейс пока не является
  принятым изменением и не реализуется.
- Не менять DNS, домен или архитектуру только из-за медленной первой загрузки:
  зафиксировать её как наблюдение custom-domain TLS/маршрута и сначала повторить
  проверку из другого сетевого окружения и проверить статус HTTPS в GitHub Pages.

### Почему

Один успешный batch доказывает, что базовая цепочка и секреты работают, но не
доказывает корректность всех режимов управления и восстановления. Разделение
«подтверждено» и «ещё не проверено» не позволяет случайно включить cron или
объявить готовой распубликацию. Медленная загрузка возникла на доступе к
custom domain после успешного Pages deploy; на уровне страницы уже проверены
разметка, четыре фотографии и отсутствие ошибок консоли, поэтому преждевременная
перестройка пайплайна не оправдана.

### Граница и проверка

- Workflow: [run 32477021777](https://github.com/5p17f1Re/5p17f1re.github.io/actions/runs/32477021777).
- Publication commit: [`dded24b`](https://github.com/5p17f1Re/5p17f1re.github.io/commit/dded24bff723b5194d48389d99dcb541f114caa3).
- Live route: [`/photos/`](https://sevakudryavtsev.com/photos/); browser-check
  подтвердил title `Photos`, четыре записи и пустой список console errors/warnings.
- Открытые проверки: `/published` → `/unpublish`, RAW, GPS privacy, пустой и
  ошибочный batch, повторный запуск, cron и причина slow first load.

Если это решение меняется, не редактировать эту запись задним числом. Добавить
новую запись с датой и явно написать, какое решение она заменяет.

## 2026-08-21 — управление снятием публикации

### Решение

- Добавить `/published`, который показывает опубликованные фотографии с номерами.
- Добавить `/unpublish 3` и множественный вариант `/unpublish 1 2`.
- Запускать снятие через тот же GitHub Actions workflow, но с input `mode = unpublish`.
- Удалять только публичные записи и производные файлы: `data/photos.json`,
  `generated/photo-media-manifest.json` и файлы соответствующего draft ID в
  `public/photos/`.
- Сохранять D1-запись, статус истории и оригиналы владельца.

### Почему

Публичный сайт остаётся статическим GitHub Pages и не должен содержать секретный
GitHub token или неподтверждённую админку. Telegram уже является закрытой точкой
управления владельца, поэтому отдельный публичный backend для v0 не нужен.
Раздельный `publication_status` позволяет безопасно повторить неудачный batch и
не выдавать запрос как выполненный до успешного Pages deploy.

### Граница и проверка

Команда не удаляет оригиналы и не очищает staging досрочно. Полный E2E
`/published` → `/unpublish` → commit → Pages → callback ещё нужно пройти после
push workflow, применения D1 migration `0005_publication_control.sql` и настройки
GitHub Actions token.

## 2026-08-20 — управление очередью и немедленная публикация

### Решение

- Добавить `/q`, который показывает только неподанный статус `ready` с
  номерами в порядке добавления.
- Добавить `/1 2 5 cancel` для отмены выбранных элементов и `/cancel all` для
  отмены всей очереди. Эти команды не прерывают уже захваченный `batching`.
- Добавить `/help` со всеми командами и `/publish`, который запускает текущий
  GitHub Actions workflow через `workflow_dispatch` сразу.
- Для вызова GitHub API использовать отдельный Worker Secret
  `GITHUB_ACTIONS_TOKEN`, ограниченный этим репозиторием и правом запуска Actions.

### Почему

Нумерованная очередь позволяет управлять публикацией из Telegram без отдельной
админ-панели. Немедленная публикация сохраняет тот же проверенный batch-пайплайн,
но не требует ждать недельного cron.

## 2026-08-20 — загрузка одним сообщением, EXIF-preview и порядок чата

### Решение

- Убрать отдельные шаги `title`, `description` и `alt`: пользователь отправляет
  один фотофайл, а подпись к Telegram-сообщению становится единственной
  необязательной пользовательской подписью.
- Сразу после загрузки показывать одну проверочную квитанцию с датой,
  человекочитаемым местом и GPS-координатами из EXIF, если они есть.
  Координаты сохраняются только в приватном EXIF preview для текущего
  publishing-flow и не публикуются на сайте.
- Показывать дату в русском формате `дд.мм.гггг` через inline-календарь.
  Кнопка пропуска означает: использовать EXIF, а при его отсутствии — дату
  загрузки, которую определит batch importer.
- До подтверждения разрешить редактировать подпись, дату и место в том же
  сообщении, чтобы фотографию не приходилось загружать заново.
- При ответе текстом удалять старый вопрос бота и отправлять новую квитанцию
  после ответа пользователя. Кнопки могут редактировать текущую квитанцию, но
  текстовый ответ не должен заставлять ленту двигаться назад.
- Принимать RAW-файлы по расширению; Telegram Cloud Bot API ограничивает
  скачивание через `getFile` файлами до 20 MB. Конвертацию RAW выполнять в
  GitHub Actions через `libraw-bin`, а затем передавать TIFF в Sharp.
- Показывать честное состояние EXIF: `EXIF отсутствует`, `не найдено в EXIF`
  или `не удалось прочитать EXIF`; внешний поиск места и reverse geocoding не
  выполняются.
- Текст из caption исходного Telegram-сообщения показывать только в поле
  «Подпись», без отдельной служебной фразы.
- Сделать review-квитанцию компактной: три строки — caption, дата с `(exif)` и
  место/координаты с `(exif)`; при отсутствии значения показывать `no date
  (exif)` или `no location (exif)`.
- Для недельного push использовать `--force-with-lease`, а не безусловный
  `--force`: при изменении `main` конкурентным commit workflow должен
  остановиться, а не перезаписать чужую работу.
- После подтверждения заменить диалог одной квитанцией вида «N фото добавили в
  очередь. Опубликуем в ближайшую среду» и перечислить выбранные значения.
  Промежуточные сообщения бота и пользователя удалить через Telegram Bot API.
- Не добавлять просмотр всей очереди на этом этапе: количество уже видно в
  квитанции, а отдельная команда появится только при реальной потребности.

### Почему

Название не используется в текущем дизайне выставки, а отдельный ручной
описательный шаг не нужен: текст уже можно приложить подписью к файлу. `alt`
остаётся техническим нейтральным fallback до отдельного решения об AI-описании.
EXIF-preview позволяет проверить данные до очереди, но не превращает R2 в архив.
Удаление старого вопроса после текстового ответа сохраняет естественный порядок
ленты, а финальная квитанция сохраняет проверяемый результат выбора.

### Граница и проверка

Для удаления входящих сообщений используется ограничение Telegram Bot API для
личных чатов; Worker хранит ID сообщений конкретного черновика только до
завершения подтверждения. Плановая дата среды соответствует cron `0 17 * * 3`
после включения расписания; до первого полного E2E cron остаётся выключенным.
Новая версия Worker задеплоена, D1-миграция `0004_review_session.sql`
применена, `/health` вернул `ok: true`; ручной Telegram E2E ещё нужно пройти.

## 2026-08-20 — v0 publishing pipeline для фотографий

Статус: архитектурное решение принято; v0 кодовый срез создан, внешние ресурсы
настроены, полный E2E ещё не выполнен.

### Решение

- Строить личный сервис публикации фотографий на бесплатном стеке Cloudflare
  Worker + D1 + приватный R2, без VPS и без обязательной ежемесячной оплаты.
- Принимать фотографии через Telegram webhook. Локальный компьютер не является
  частью обычного upload-flow.
- Сохранять рабочую копию и состояние сразу, а Git commit и Pages deploy выполнять
  одним недельным batch. Первоначальный запуск workflow — ручной, cron включается
  только после E2E-проверки.
- Считать R2 временным staging для копий, а не архивом. Оригиналы хранятся у
  владельца в двух локальных копиях; после подтверждённой публикации staging
  сохраняется семь дней и затем очищается.
- Публиковать только подготовленные производные через GitHub Pages. R2 не
  становится публичным источником изображений.
- Держать Telegram/Worker, batch importer и статический сайт в одном репозитории
  `site-nextjs`, но разделить media ownership: существующий `public/media/`
  кейсов и отдельный `public/photos/` для нового раздела.
- Автоматически извлекать технические метаданные, но не публиковать GPS и полный
  EXIF. Дата выбирается в порядке «ручная → EXIF → дата загрузки».
- Добавить `/photos/` и `/ru/photos/`, группировку по году и месяцу и сначала
  показывать ссылку на раздел в footer. Автоматический перевод и полноценный
  backend/auth для публичного пароля в v0 не входят.
- Не использовать имя владельца в инфраструктуре. Зафиксировать нейтральные
  имена Worker `photo-publisher-5555`, D1 `photo-publisher-5555-db`, R2
  `photo-publisher-5555-staging`; отображаемое имя Telegram-бота — `Photo
  Publisher`. Суффикс `5555` нужен только для уникальности.

### Почему

Пользовательский сценарий нерегулярный: фотографии могут загружаться в течение
недели, а затем не публиковаться месяцами. Поэтому данные и черновики должны
фиксироваться сразу, но постоянный сервер и непрерывный процесс не нужны.
GitHub Pages уже является публичным статическим слоем сайта, а личные оригиналы
не должны попадать в новый сервис. Отдельный выход для фотографий нужен потому,
что текущий `prepare-media` синхронизирует `public/media/` и может удалять
неожиданные файлы.

### Граница и проверка

Подробный flow, статусы, секреты, этапы и критерии готовности находятся в
[`docs/photo-publishing-plan.md`](photo-publishing-plan.md). При реализации
решение будет проверено ручным E2E «Telegram → R2/D1 → batch → commit → Pages»
и стандартными проверками сайта.

Кодовый срез и локальная проверка выполнены 2026-08-20: root TypeScript,
Worker TypeScript, 14 тестов, ESLint без новых ошибок, production build,
Wrangler dry-run и browser-render обоих photo-маршрутов. Worker, D1, R2 и
Telegram webhook настроены; полный E2E, реальные EXIF/GPS-выходы и R2 API key
для GitHub Actions ещё требуют проверки.

## 2026-08-17 — footer navigation и единая motion-система первого экрана

Коммит: `d24b9e1` (`Fix footer navigation and mobile motion`)

### Решение

- Упростить навигацию кейса и убрать клонирование case shell для переключения языка.
- Держать языковую ссылку в footer, а не запускать отдельный overlay поверх страницы кейса.
- Привязать появление Telegram CTA к готовности измеренных строк About и использовать
  фиксированные `250 ms` задержки, `350 ms` длительности и `blur(12px)`.
- Сохранить общий stagger карточек и начинать первый ряд через `310 ms`.
- Учесть высоту footer в позиции мобильной навигации через
  `--mobile-nav-footer-offset`.

### Почему

Отдельная копия case shell и независимые таймеры создавали конкурирующие переходы,
лишний DOM и риск рассинхронизации при смене языка. Привязка CTA к готовности строк
делает первый экран устойчивым к разной ширине viewport, а footer-offset не даёт
мобильной навигации пересекаться с нижним контентом.

Проверка локализованных footer labels добавлена в `tests/localization.test.ts`.

### Уточнение причин и границ решения

Это уточнение относится к коммиту `d24b9e1` и фиксирует финальные требования к
композиции footer и мобильной навигации:

- Контакты, языковая ссылка и служебная информация остаются отдельными строками:
  после контактов — `12 px`, после «По-русски» / `In English` — ещё `12 px`,
  после даты обновления дополнительного отступа нет.
- Языковая ссылка строится от текущего маршрута, поэтому `/ru/` открывает ту же
  страницу на английском, а английская страница — соответствующую русскую
  страницу. Если парного маршрута нет, ссылка не показывается.
- На мобильном footer не перекрывается fixed-навигацией: при попадании footer в
  viewport навигация поднимается измеряемым offset так, чтобы между ними
  сохранялось `32 px`. На desktop это поведение не включается.
- Кнопки навигации используют content-sized (`hug`) ширину и единый padding;
  стили, рассчитанные на фиксированную ширину отдельных кнопок, удалены.
- Финальные motion-значения остаются явными: Telegram начинает reveal через
  `250 ms` после завершения About, сам reveal длится `350 ms`, а карточки кейсов
  начинают появляться через `310 ms` с последующим stagger.

Причина такой структуры — не маскировать разные смысловые группы одним общим
селектором отступов: общий `p + p` добавлял лишний зазор перед версией. Маршрутная
ссылка сохраняет контекст кейса и не отправляет пользователя на главную страницу.
Измеряемый offset нужен потому, что высота footer и fixed-навигации меняется на
разных мобильных viewport; постоянный bottom offset оставлял бы перекрытие или
лишнее пустое место. Content-sized кнопки предотвращают разные внутренние поля
у коротких и длинных подписей, а финальные задержки разделяют текстовый reveal и
появление интерактивных блоков без зависимости от фиксированной паузы до About.

## 2026-08-18 — lazy playback и mobile case media

Коммит: `c33c371` (`Fix mobile case media spacing and lazy playback`)

### Решение

- Для общего `CasePhoneMedia` загружать и запускать видео только при попадании в
  viewport; при выходе ставить его на паузу. При `prefers-reduced-motion` autoplay
  не запускается.
- Показывать clipboard-success только после подтверждённого успеха Clipboard API
  или `document.execCommand("copy")`; не отправлять контактное событие при неудаче.
- Для всех мобильных `CasePhoneMedia` использовать `24 px` вертикальных и `32 px`
  горизонтальных внутренних отступов. Экран получает доступную ширину внутри этих
  отступов, поэтому правило применяется к PYE и будущим мобильным скриншотам.

### Почему

Ранее все phone-видео запускались при mount, поэтому дальние ролики PYE начинали
загрузку и декодирование до прокрутки. Clipboard fallback игнорировал возвращаемое
значение и мог показывать ложный toast. Явные внутренние отступы дают одинаковую
рамку мобильным скриншотам и не меняют desktop-геометрию.

Проверено: ESLint (0 ошибок; остались 2 прежних warning для Telegram `<img>`),
TypeScript, 12 тестов, production build и `git diff --check`. Серверная разметка
показывает для phone-видео начальные `preload="none"` без `src` до viewport.

## Постоянное правило

Каждое принятое изменение сайта сопровождается записью в этом журнале в том же
рабочем цикле: дата, коммит, решение, причина, затронутая граница и проверка.
Коммит и push не должны быть единственным местом, где объяснено поведение.
