# Эксперимент: переход карточка → обложка кейса

Статус: в работе. Ни одна экспериментальная ветка не слита в `main` и не
отправлена в remote.

Документ описывает не только PYE. PYE использовался как первый проверочный кейс,
но архитектура перехода должна одинаково работать для всех карточек с
`transitionId`, в Birdview и Snakeview. Это исторический документ эксперимента:
текущие production-правила и параметры находятся в
[системе motion](motion-system.md).

## Цель

Связать карточку проекта на главной с первым медиаблоком кейса, не заставляя
пользователя наблюдать длинный полёт через весь экран.

Желаемое ощущение:

1. пользователь видит начало движения карточки с главной;
2. середина пространственного перехода скрыта короткой склейкой;
3. пользователь видит появление обложки кейса;
4. при возврате последовательность работает в обратном направлении;
5. ни один этап не заканчивается геометрическим скачком или морганием медиа.

## Сохранённые версии

### 1. Ручной DOM-overlay

- Ветка: `codex/pye-cover-transition-experiment`.
- Коммит: `446bce9` — `Save shared cover transition experiment`.
- Статус: сохранён для истории, не использовать как основу новой реализации.

Переход собирался из ручного overlay, измерений DOM и нескольких независимых
таймеров. Он доказал направление, но ownership состояния оказался распределён
между страницей, навигацией, карточкой и CSS. При смене маршрута возникали
скачки координат, промежуточный `scrollY = 0` и моргание poster/video.

### 2. Непрерывный shared-layout на Motion

- Ветка: `codex/case-cover-transition-motion`.
- Коммит: `6db81d8` — `Build case cover transitions with Motion`.
- Статус: рабочая контрольная версия, сохранена локально.

Motion `layoutId` универсально связывает карточку и первый медиаблок кейса. Эта
версия надёжнее ручного overlay и правильно вычисляет траекторию между реальными
прямоугольниками в Birdview и Snakeview.

Причина следующего эксперимента: непрерывный полёт слишком длинный и заставляет
смотреть на морфинг разных изображений. Особенно заметен последний момент
совмещения геометрии и контента.

### 3. Монтажный переход

- Ветка: `codex/case-cover-cut-transition`.
- База: коммит `6db81d8`.
- Статус: текущий незакоммиченный эксперимент, ожидает визуальной приёмки.

Главный принцип: сохранить правильное пространственное направление из второй
версии, но не показывать середину полёта.

## Актуальная спецификация третьей версии

### Production-параметры

| Параметр | Значение |
| --- | --- |
| Запуск навигации после клика | Birdview: `200 ms`; Snakeview: `250 ms` |
| Длительность направленного движения `x/y` и scale | `300 ms`; handoff зависит от режима |
| Takeoff easing | `cubic-bezier(0.45, 0, 0.75, 0.65)` |
| Landing | `350 ms` |
| Landing easing обложки | `cubic-bezier(0.12, 1, 0.2, 1)` |
| Landing easing прозрачности | `cubic-bezier(0.4, 0, 0.2, 1)` |
| Появление обложки кейса | `scale 0.9 → 1`, `y 48px → 0`, `opacity 0 → 1` |
| Исчезновение текста активной карточки | `150 ms` |
| Появление текста активной карточки | задержка `350 ms`, затем `opacity 0 → 1`, `blur 24 → 0` за `150 ms`; конец на `500 ms` |
| Соседние карточки при входе | `opacity 1 → 0.6`, `blur 0 → 24px`, `300 ms`, takeoff easing |
| Соседние карточки при возврате | задержка `150 ms`, затем `opacity 0.6 → 1`, `blur 24 → 0` за `350 ms`, landing easing; конец вместе с текстом на `500 ms` |
| Gradient reveal заголовка кейса | `350 ms` |
| Возврат из глубины кейса | `450 ms`, `scale 1.2 → 1`, `blur 12 → 0` |
| Takeoff-scale в Birdview | `1 → 1.35` за `300 ms`, синхронно с `x/y`; cut на `200 ms` |
| Takeoff-scale в Snakeview | адаптивный, максимум `1.07` |
| Пространственный вектор | `1.1` расстояния от центра карточки до расчётного центра обложки |

Под текстом активной карточки в этой таблице понимаются три элемента вместе:
заголовок, описание и кнопка `Read Case`.

Активная карточка на время takeoff поднимается над соседними карточками отдельным
слоем. Это обязательно для карточек, которые при увеличении пересекают соседнюю
ячейку: например, Starter Stories больше не должна уходить под AVGVST.

### Вход в кейс

1. До смены маршрута контроллер измеряет DOM-прямоугольник медиаблока активной
   карточки. Из него рассчитываются направление к центру будущей широкой обложки,
   увеличение и видимый начальный отрезок траектории. Расчёт выполняется заново
   для фактической позиции карточки, поэтому работает в Birdview и Snakeview.
2. Координаты `x/y` и увеличение работают синхронно: `300 ms` и одна кривая
   `cubic-bezier(0.45, 0, 0.75, 0.65)`. В Birdview навигация запускается на
   `200 ms`, чтобы карточка не успевала долететь до центра и видимая часть
   сильнее читалась как импульс на зрителя. В Snakeview handoff остаётся на
   `250 ms`. Остаток общего движения вырезается одной склейкой без
   промежуточного возврата transform.
3. Заголовок, описание и `Read Case` активной карточки уходят
   `opacity 1 → 0` за `150 ms`.
4. Остальные карточки переходят к `opacity: 0.6` и `blur(24px)` за `200 ms`.
5. Отдельной паузы или пустого cut-кадра нет. Landing запускается в layout effect
   сразу после фактического монтирования целевого маршрута.
6. Обложка кейса появляется целиком относительно центра: `scale 0.9 → 1`,
   `y 48px → 0`, `opacity 0 → 1`, длительность `350 ms`. Transform сохраняет
   сильное затухание landing, а opacity использует отдельную более спокойную
   кривую без резкого появления. При возврате движение зеркальное:
   `scale 1 → 0.9`, `y 0 → 48px`.
7. Takeoff использует `cubic-bezier(0.45, 0, 0.75, 0.65)`: в точке смены маршрута
   карточка находится в быстрой части кривой. Landing использует
   `cubic-bezier(0.12, 1, 0.2, 1)` и заметнее гасит полученный импульс длинным
   плавным хвостом.
8. Изображение или видео внутри обложки не получает отдельного transform. Должен
   двигаться весь медиаблок, а не его содержимое.

### Отзывчивость навигации

Состояние активного перехода должно завершаться одновременно с визуальным концом
соответствующего landing. Скрытый запас после анимации запрещён: прежние
дополнительные `300 ms` оставляли контроллер занятым уже после остановки обложки,
поэтому первый клик по возврату перехватывался без действия, а навигация
срабатывала только со второго раза. При входе состояние снимается через `350 ms`
после монтирования кейса; при возврате — через `500 ms`, одновременно с концом
blur и проявления текста карточки.

### Заголовок кейса

Заголовок должен быть скрыт с первого кадра нового маршрута. Только после начала
landing-фазы он один раз появляется горизонтальной градиентной маской.

Запрещённое состояние: сначала виден настоящий заголовок, затем он исчезает и
после этого появляется повторно из градиента.

### Возврат на главную

1. Видимая обложка кейса уменьшается относительно собственного центра.
2. Навигация запускается на движении, без отдельной паузы.
3. После восстановления scroll карточка главной монтируется в своём настоящем
   прямоугольнике с сохранённым направленным transform и завершает движение к
   `x: 0`, `y: 0`, `scale: 1`.
4. Соседние карточки одновременно возвращаются из `opacity: 0.6` и
   `blur(24px)` в обычное состояние с задержкой `100 ms` и длительностью
   `400 ms`.
5. Заголовок, описание и `Read Case` активной карточки остаются скрыты до полного
   окончания её landing-анимации и затем появляются за `150 ms`.
   Обе линии заканчиваются одновременно на отметке `500 ms` от начала landing.
6. Сохранённые вид главной и позиция прокрутки восстанавливаются до видимого
   landing-этапа.

Если обложка кейса находится вне viewport, нельзя изображать полёт с края
страницы. Для такого возврата сохраняется локальный fallback появления карточки
на главной длительностью `450 ms`: `scale 1.2 → 1`, `opacity 0 → 1`,
`blur 12px → 0`.

## Ownership и основные файлы

- `components/CaseCoverMotion.tsx` — единственный владелец snapshot, направления,
  фаз, рассчитанного вектора, навигации, восстановления scroll и Motion-анимации.
- `components/SiteShell.tsx` — постоянное место провайдера между маршрутами.
- `components/Portfolio.tsx` — сообщает контроллеру выбранный проект, view и
  исходную позицию; не владеет таймлайном.
- `components/CaseMedia.tsx` и `components/CaseVideo.tsx` — помечают первый
  медиаблок кейса как target.
- `styles.css` — blur/opacity соседей, fade текста карточки, reveal заголовка и
  offscreen fallback.

Не добавлять отдельные таймеры перехода в страницы конкретных кейсов,
`Navigation` или `Portfolio`.

### Почему маршрут не обёрнут в AnimatePresence

Next.js App Router обновлял `children` внутри обоих элементов
`AnimatePresence`. Вместо сохранённой главной в DOM оказывались две копии уже
нового кейса: одна `position: absolute` со смещением примерно `120px`, другая в
нормальном layout. При удалении первой копии обложка и заголовок совершали
финальный вертикальный скачок.

Поэтому `CaseMotionRoutes` не удерживает две страницы одновременно. Навигация
запускается во время takeoff, а landing начинается после монтирования нового
маршрута. Это исключает дубли страниц, паузу между фазами и самопроизвольные
layout-анимации при reload.

### Фазы

- `takeoff` — исходный маршрут остаётся в DOM, активная обложка движется;
- `landing` — целевой маршрут уже смонтирован, целевая обложка движется к
  собственному финальному состоянию;
- `idle` — data-атрибуты и transforms удалены.

## Медиа

- Карточка и обложка могут использовать разные изображения. Склейка должна
  скрывать их замену; морфить содержимое картинок не требуется.
- Poster остаётся под видео до первого реально отрисованного видеокадра.
- Poster и video сменяются только opacity-переходом и не должны оставлять чёрный
  или пустой кадр.
- Старые case entrance-анимации не должны одновременно двигать первый медиаблок.

## Отдельная известная проблема

Одиночный клик Birdview/Snakeview и языка технически менял состояние сразу, но
интерфейс оставался в переходном состоянии `500 ms` и `260 ms` соответственно.
Это воспринималось как потерянный первый клик. В отдельной правке длительность
переключения вида сокращена до `320 ms`, а языкового layout — до `180 ms`.

## Как продолжать работу

1. Прочитать корневой `README.md`, затем этот документ целиком.
2. Проверить текущую ветку и рабочее дерево. Не предполагать, что третий вариант
   уже принят или закоммичен.
3. Менять один параметр характера движения за раз и оставлять localhost для
   пользовательской проверки.
4. Перед каждым новым вариантом показать план и получить подтверждение.
5. Не коммитить третий вариант до визуальной приёмки пользователя.
6. Не сливать экспериментальные ветки в `main` и не пушить без отдельного
   запроса.

Для возврата к сохранённым вариантам достаточно переключиться на соответствующую
ветку. Локальные коммиты `446bce9` и `6db81d8` остаются точками восстановления.
