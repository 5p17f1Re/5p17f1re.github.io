# План сервиса публикации фотографий

Статус: Worker, D1, R2 и Telegram webhook настроены. Базовый реальный E2E
публикации пройден 2026-08-21 на batch из четырёх фотографий: Telegram → R2/D1
→ GitHub Actions → commit → GitHub Pages → callback Worker. Управление снятием
публикации, RAW/GPS-проверки, failed/empty batch и weekly cron ещё не закрыты.

Этот документ — канонический план для Telegram → Cloudflare → GitHub Pages
пайплайна. В следующих чатах сначала нужно читать этот файл и
[`decision-log.md`](decision-log.md), а уже потом обсуждать или менять код.
Новые решения, которые меняют этот план, сначала добавляются в журнал решений,
затем отражаются здесь.

Практическая настройка Cloudflare, Telegram и GitHub Secrets вынесена в
[`photo-publishing-setup.md`](photo-publishing-setup.md), чтобы не смешивать
архитектуру с одноразовыми командами.

## 1. Что мы строим

Это сервис публикации копий фотографий в интернет и отдельный раздел сайта
`/photos/`. Это не архив и не система резервного хранения.

Оригиналы фотографий остаются у владельца в двух копиях. Telegram-сервис
принимает рабочие копии, готовит из них публичные производные и публикует их на
сайте. Если временная копия в staging потеряна до публикации, фотографию можно
загрузить заново из оригинала.

Цель v0 — получить надёжный личный publishing pipeline без VPS и обязательных
ежемесячных расходов, с возможностью постепенно превратить портфолио в личное
интернет-пространство: сначала фотографии, затем ссылки с главной и позже
статьи.

## 2. Принятая архитектура

```text
Telegram
  ↓ webhook
Cloudflare Worker
  ├─ D1: состояние диалога, метаданные, статусы публикации
  └─ приватный R2: временные копии до недельной публикации
             ↓ workflow_dispatch / weekly cron
GitHub Actions
  ├─ читает batch из Worker и забирает файлы из R2
  ├─ Sharp + EXIF-подготовка публичных производных
  ├─ записывает JSON и public/photos/<year>/<month>/
  ├─ делает один commit/push
  └─ собирает и деплоит статический сайт на GitHub Pages
             ↓
Публичный сайт: sevakudryavtsev.com/photos/
```

### Компоненты

- **Telegram Bot** — единственная точка загрузки и ввода метаданных.
- **Cloudflare Worker Free** — webhook и маленький backend для авторизованного
  владельца.
- **Cloudflare D1 Free** — источник состояния очереди и метаданных до публикации.
- **Cloudflare R2 Free** — приватный временный staging. R2 не используется как
  публичный CDN и не является каноническим архивом.
- **GitHub Actions** — недельный batch, подготовка медиа, commit и деплой.
- **GitHub Pages** — публичная раздача HTML и готовых конвертированных файлов.
- **Next.js static export** — текущий frontend остаётся статическим; Worker не
  встраивается в публичный сайт.

Имена инфраструктуры нейтральные: Worker `photo-publisher-5555`, D1
`photo-publisher-5555-db`, R2 `photo-publisher-5555-staging`. В Telegram бот
может называться `Photo Publisher`, а его уникальный `@username` выбирается в
BotFather и может отличаться.

Worker и сайт находятся в одном репозитории `site-nextjs/`, чтобы код,
миграции, workflow и документация имели один source of truth. Worker будет
отдельным workspace-пакетом `publisher-worker/` и не станет частью Next.js
сборки.

## 3. Как работает публикационный цикл

### 3.1. Сразу при загрузке

1. Пользователь отправляет фотофайл в Telegram; подпись к этому же сообщению
   становится необязательной подписью фотографии.
2. Worker проверяет секрет webhook и разрешённый `chat_id`.
3. Worker скачивает файл из Telegram и сразу сохраняет его в приватный R2.
4. Worker создаёт запись в D1 со статусом `collecting` и читает короткий EXIF
   preview: дату, человекочитаемое место и GPS-координаты для показа владельцу
   в квитанции. Координаты не попадают в публичные производные сайта.
   Поддерживаются обычные изображения и RAW-файлы по имени расширения.
5. Бот отправляет одну квитанцию: что найдено в EXIF и какая подпись пришла из
   Telegram. Отдельного шага для описания или alt-текста нет.
   Формат квитанции компактный и без поясняющих labels:
   ```text
   подпись из Telegram
   29.03.2026 (exif)
   55.7558, 37.6173 (exif)
   ```
6. До подтверждения можно кнопками изменить подпись, дату или место. Если
   пользователь отвечает текстом, старый вопрос удаляется, а новая квитанция
   отправляется ниже ответа — порядок сообщений в чате остаётся естественным.
7. После подтверждения черновик получает статус `ready`, а сообщение заменяется
   одной компактной квитанцией с количеством фотографий в очереди и выбранными
   значениями. Промежуточные сообщения диалога и ответы пользователя удаляются;
   отдельный просмотр всей очереди пока не нужен.

Для управления публикацией есть команды `/help`, `/q`, `/1 2 5 cancel`,
`/cancel all` и `/publish`. Нумерация очереди выдаётся командой `/q` в порядке
добавления. Для уже опубликованных фотографий `/published` показывает отдельную
нумерацию, а `/unpublish 3` запрашивает снятие выбранной производной с сайта.
`/publish` и `/unpublish` запускают один и тот же GitHub Actions workflow с разным
режимом и требуют отдельного Worker Secret `GITHUB_ACTIONS_TOKEN`.

Telegram Cloud Bot API ограничивает скачивание через `getFile` файлами до 20 MB.
Поэтому RAW-файл принимается в v0 только в пределах этого лимита. На недельном
GitHub batch для RAW устанавливается `libraw-bin`, файл переводится во временный
TIFF, а затем проходит общий Sharp-пайплайн. Если понадобится принимать RAW
больше 20 MB, это будет отдельное решение: прямой upload или собственный
Telegram Bot API server.

До подтверждения фотография не попадает в batch. Отменённые или ошибочные
черновики не публикуются автоматически.

### 3.2. В конце недели

Первый запуск будет ручным через `workflow_dispatch`, чтобы проверить полный
цикл. После успешного E2E можно включить расписание: среда, 20:00 по
Москве. Расписание является удобством, а не частью модели данных: если за
полгода ничего не загружено, workflow ничего не публикует.

Batch делает следующее:

1. Запрашивает у Worker подтверждённые записи со статусом `ready`.
2. Помечает их `batching`, чтобы параллельный запуск не взял их повторно.
3. Читает исходные копии из R2 через scoped R2 credentials.
4. Извлекает технические данные и готовит публичные варианты.
5. Не публикует GPS и полный EXIF. Координаты могут быть показаны владельцу в
   приватной Telegram-квитанции, но не переходят в публичный JSON или HTML.
   Публичными могут быть только заранее
   разрешённые поля: дата, размеры, камера, объектив и человекочитаемое место.
   Ручная подпись пользователя публикуется как caption; технический `alt`
   получает нейтральный fallback `Фотография`, пока отдельное AI-описание не
   будет принято как самостоятельное решение.
6. Записывает публикационный JSON и готовые медиа в Git.
7. Делает один commit на весь недельный batch.
8. Публикует commit через `force-with-lease`: batch не должен застревать из-за
   ожидаемого замещения сгенерированного состояния, но workflow остановится,
   если `main` изменился после checkout. Безусловный `--force` не используется.
9. Собирает Next.js и деплоит GitHub Pages в том же workflow. Это важно, потому
   что push с `GITHUB_TOKEN` не должен зависеть от повторного запуска другого
   workflow.
10. После успешного деплоя сообщает Worker commit SHA и переводит записи в
   `published`.
11. R2-копии сохраняются ещё семь дней после успешной публикации, затем
   удаляются Worker cleanup-задачей. До подтверждённого деплоя они не удаляются.

### 3.3. Снятие уже опубликованной фотографии

1. `/published` читает из D1 только записи с `publication_status = published` и
   показывает их с номерами.
2. `/unpublish 3` или `/unpublish 1 2` помечает выбранные записи как
   `unpublish_requested` и запускает workflow в режиме `unpublish`.
3. Worker захватывает такие записи как отдельный batch, а importer удаляет их
   из `data/photos.json`, `generated/photo-media-manifest.json` и только
   производные файлы с соответствующим draft ID в `public/photos/`.
4. После успешного Pages deploy запись в D1 получает
   `publication_status = unpublished`. История и D1-запись сохраняются, а
   оригинал владельца не затрагивается.
5. Если workflow или Pages завершается ошибкой, запрос возвращается в
   `unpublish_requested`; публичная запись не считается снятой.

Распубликация не является удалением оригинала и не очищает staging досрочно.
Публичная копия исчезает из следующего Pages deploy; GitHub history и CDN-кэш
могут ещё некоторое время содержать старый commit или URL.

## 4. Состояния данных

Для фотографии используются следующие статусы:

- `collecting` — бот ещё собирает метаданные;
- `ready` — пользователь подтвердил публикацию;
- `batching` — запись захвачена недельным запуском;
- `committed` — производные записаны в Git и commit создан;
- `published` — Pages-деплой подтверждён;
- `publication_status` дополнительно описывает публичный слой: `not_published`,
  `published`, `unpublish_requested`, `unpublishing` или `unpublished`;
- `failed` — batch завершился ошибкой, запись можно повторить;
- `cancelled` — пользователь отменил черновик.

Важное правило: статус `published` ставится только после успешной публикации
сайта, а не после одного `git commit`.

## 5. Метаданные и приватность

### Приоритет даты

```text
ручная дата → дата из EXIF → дата загрузки в Telegram
```

Дата сохраняется в ISO-формате и используется для группировки по году и месяцу.
В Telegram она показывается пользователю в русском формате `дд.мм.гггг`.

### Что публикуем

- публичную копию изображения в AVIF/WebP и fallback JPEG;
- размеры изображения и orientation после нормализации;
- дату съёмки;
- камеру и объектив, если они есть и пользователь не запретил их показывать;
- пользовательскую подпись из caption Telegram;
- необязательное текстовое место, если его ввёл пользователь.

### Что не публикуем

- оригинальный файл;
- GPS-координаты;
- полный EXIF;
- Telegram `file_id`, chat ID, внутренние ключи R2 и D1;
- секреты, токены и внутреннюю историю ошибок.

Отдельное ручное описание убрано из v0. До подключения AI публичный batch
использует нейтральный `alt`-fallback; это временная техническая граница, а не
попытка выдать автоматически созданное описание за редакционный текст.

## 6. Граница сайта и файлов

Текущий медиапайплайн кейсов (`prepare-media`) остаётся отдельным. Он
деструктивно синхронизирует `public/media/`, поэтому фото-публикация не должна
переиспользовать его выходную папку.

Для фотографий вводится отдельная граница:

```text
data/photos.json
data/photos.ts
generated/photo-media-manifest.json
public/photos/<year>/<month>/...
scripts/import-photo-batch.mjs
```

Публичные маршруты:

- `/photos/` — английская версия;
- `/ru/photos/` — русская версия.

На первом шаге фотографии группируются по году и месяцу. Контент может быть
общим для двух языков; автоматический перевод в v0 не выполняется. Ссылка на
раздел сначала появляется в footer, когда опубликована хотя бы одна фотография.
Отдельный блок на главной добавляется следующим этапом после проверки базового
раздела.

## 7. Безопасность и стоимость

- R2 bucket остаётся приватным; публичный сайт читает только GitHub Pages.
- Telegram webhook принимает только запросы с настроенным secret token и от
  разрешённого chat ID.
- Внутренние endpoints Worker защищены отдельным токеном GitHub Actions.
- GitHub Secrets хранят Telegram token, webhook secret, Worker internal token и
  R2 credentials; в репозитории этих значений быть не должно.
- R2 credentials для batch ограничиваются чтением staging и не используются в
  браузере.
- Данные в D1 — очередь публикации, а не единственное хранилище оригиналов.
- Бесплатный стек подходит для нерегулярного личного процесса; бесплатные
  лимиты и доступность Cloudflare из России нужно проверить реальным E2E.
- Для публичного доступа не требуется доступ пользователя к Cloudflare: после
  деплоя HTML и производные находятся на GitHub Pages. Доступ к Cloudflare
  Dashboard/API может потребовать VPN при настройке и диагностике.

## 8. Что намеренно не входит в v0

- VPS, dedicated server или постоянный backend на отдельном хостинге;
- публичная раздача изображений напрямую из R2;
- полноценная админ-панель на сайте; управление v0 выполняется в Telegram;
- парольная защита статического GitHub Pages;
- автоматический перевод подписей;
- публикация в Instagram;
- архивирование оригиналов или замена двух локальных копий;
- сложные коллекции, лайки, комментарии и пользовательские аккаунты.

Эти пункты могут появиться после накопления реального сценария использования.
Публичный парольный доступ потребует отдельного backend/auth-слоя и не должен
маскироваться клиентским условием в статическом HTML.

## 10. Критерии готовности v0

v0 считается готовым, когда:

1. фото можно отправить только через Telegram, без запуска локального компьютера;
2. после загрузки копия и состояние сохраняются сразу;
3. неподтверждённый черновик не публикуется;
4. недельный запуск создаёт один согласованный commit;
5. ошибка подготовки или Pages не приводит к удалению staging-копии;
6. повторный запуск не создаёт дубликаты;
7. опубликованный сайт показывает фотографии по годам и месяцам на обоих
   языковых маршрутах;
8. в Git и публичных файлах нет GPS, Telegram secrets и оригиналов;
9. после паузы в несколько месяцев процесс можно возобновить новой загрузкой;
10. доступность Cloudflare-настройки и публичного GitHub Pages проверена из
    реального пользовательского окружения.
