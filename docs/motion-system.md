# Система motion

Это канонический источник текущих правил движения сайта. Перед изменением
таймингов или добавлением новой анимации сначала прочитать этот документ,
затем сверить описание с кодом. Обязательное правило для следующих задач
закреплено в корневом [`AGENTS.md`](../AGENTS.md).
Исторические варианты перехода карточки в кейс хранятся в
[`pye-cover-transition-experiment.md`](pye-cover-transition-experiment.md), но
не задают production-параметры.

## Общие правила

- Motion не должен менять смысл или порядок контента: начальное состояние
  должно быть читаемым при отключённой анимации.
- `prefers-reduced-motion` отключает entrance- и shared-cover-анимации.
- Не смешивать две независимые анимации одного элемента. В частности, текст не
  должен сначала появиться обычным образом, затем скрыться и проявиться маской.
- Для перехода карточка ↔ кейс владельцем таймлайна остаётся
  `components/CaseCoverMotion.tsx`; страницы кейсов и `Portfolio` не получают
  отдельных таймеров этого перехода.
- `var(--color-background)` — единый фон главной, кейсов, PYE, 404, footer
  и самого transition layer. Переход не добавляет отдельный цвет фона: под
  маской всегда остаётся тот же токен.

### Выбор характера движения

- Все авторские анимации сайта используют spring без отскока (`bounce: 0`),
  включая перемещение, изменение масштаба, opacity, blur, маски, hover и
  курсорные эффекты. Это принцип движения, вдохновлённый докладом Apple
  [Animate with springs, WWDC23](https://developer.apple.com/videos/play/wwdc2023/10158/):
  движение сохраняет ощущение непрерывности и мягко останавливается у цели,
  не перескакивая её.
- Скорость подбирается отдельно для каждого эффекта через `duration` и
  `delay`; единой длительности для всего сайта нет. В Motion у пространственных
  переходов следующий визуальный владелец появляется только после фактического
  завершения animation controls, а не по таймеру.
- Нативный Motion spring используется для переходов обложки, смены раскладки,
  появления и локального crossfade текста, а также прокрутки наверх. Геометрия
  обложки запускается через `animate` из `motion/mini` с генератором `spring`
  из `motion`; `motion/mini` оставляет выполнение на Web Animations API и не
  оставляет временный transform в MotionValues React-компонентов.
- CSS не умеет запускать генератор Motion spring напрямую. Поэтому обычные CSS
  переходы используют `--spring-zero-bounce-easing`: `linear()`-аппроксимацию,
  снятую с Motion spring `duration: 320 ms`, `bounce: 0`. Это кусочно-линейное
  представление из 12 точек формы spring, а не нативный spring Motion; оно
  сохраняет безотскочную кривую, но не переносит скорость при прерывании и смене
  цели.
  Использовать его для коротких CSS-состояний, где перенос скорости не нужен.
  Для движения с новым курсором или другой переменной целью нужен Motion spring
  либо точный шаг решателя в `lib/zero-bounce-spring.ts`.
- В ходе этой работы sampled CSS-кривую временно применили к полёту обложки.
  Это была неверная замена: аппроксимация не давала поведения нативного Motion
  spring и визуально ухудшила пространственный переход. В финальной версии
  обложка снова использует нативный Motion spring; `linear()` остался только для
  коротких CSS-состояний. Не переносить эту аппроксимацию обратно на геометрию
  shared-cover.
- Пользовательские RAF-сглаживания курсора используют точное решение уравнения
  критически затухающей пружины в `lib/zero-bounce-spring.ts`; скорость
  сохраняется при каждом обновлении цели. Это явно ограниченная техническая
  особенность курсорных followers, а не замена Motion spring в переходе
  обложки. Шаг времени ограничен после паузы вкладки.
- Не смешивать две независимые анимации одного элемента. Начальное состояние
  должно оставаться читаемым при отключённом движении.
- `prefers-reduced-motion` отключает entrance- и shared-cover-анимации,
  курсорные followers и сокращает CSS motion. Навигационная прокрутка в этом
  режиме выполняется мгновенно.

## Решения ветки `motion/apple-zero-bounce-springs`

Ниже для каждой группы записаны текущее поведение, причина и предыдущий вариант.
«Раньше» означает состояние кода перед этой веткой; для подмены обложки также
зафиксированы варианты, которые мы пробовали при просмотре локальной версии.

### Перелёт обложки карточка ↔ кейс

- **Сейчас:** нативный Motion spring `bounce: 0`: вход `640 ms`, видимый
  возврат `480 ms`, возврат после прокрутки `450 ms`. Кадр обложки и геометрия
  удерживаются до handoff; таймлайн ждёт окончания animation controls.
- **Почему:** сохранили выбранный темп, но заменили заданные cubic-bezier на
  непрерывное пружинное затухание без отскока. При возврате после глубокой
  прокрутки нет видимого источника траектории, поэтому карточка возвращается
  локальным масштабом вместо полёта через экран.
- **Раньше:** вход использовал cubic-bezier `[0.16, 1, 0.3, 1]`, возврат —
  `[0.12, 1, 0.2, 1]`. До рефакторинга жизненного цикла 20.09 независимые
  таймеры могли отсчитывать анимацию до готовности назначения или replacement
  image; это съедало видимую часть движения. Текущая ветка сохраняет общие
  фазы `preflight`/`landing`/`handoff` и меняет их кривую и синхронизацию.

### Передача изображения обложки

- **Сейчас:** при входе crossfade запускается без заданной паузы с полётом и
  длится `160 ms` после готовности целевого изображения.
  При видимом возврате изображения смешиваются `150 ms` около точки `50%`
  spring-прогресса; это середина пройденного пути, не половина времени.
  Перед переходом снимается bitmap текущего отрисованного кадра вместе с crop;
  содержимое компенсирует разницу пропорций обложки и карточки. При возврате
  после прокрутки сразу используется homepage cover без crossfade.
- **Почему:** убрали паузу на входе и скачок в конце возврата. Смена изображения
  идёт пока обложка движется, а сохранённые crop и пропорции не дают увидеть
  перемонтированный плейсхолдер или растянутый кадр.
- **Раньше:** код до этой ветки ждал `48 ms` перед fade `160 ms` на входе и
  `64 ms` перед fade `200 ms` при возврате. В промежуточной настройке возврата
  замену пробовали в последних `50 ms`, затем увеличили fade до `150 ms`;
  скачок всё ещё был заметен, поэтому смену перенесли к середине spring-пути.
  В самой проблемной итерации без frame snapshot возврат мог перемонтировать
  изображение и показать плейсхолдер или растянутый кадр.

### Фон и blur при входе и возврате

- **Сейчас:** фоновые эффекты короче полёта обложки и занимают `75%` его
  фактической длительности. При входе с начала движения проявляется fixed
  подложка с лёгким `backdrop-filter: blur(6px)` на desktop (`3px` на mobile).
  При возврате в последние `75%` восстанавливается homepage-полотно:
  `scale: .94 → 1`, `opacity: .33 → 1`, `blur: 18px → 0`. Fixed-подложка при
  возврате сама blur не добавляет.
- **Почему:** движение обложки длиннее фонового эффекта. На входе фон начинает
  меняться в первой части перехода; при возвращении фон проясняется в последней
  части, и обложка остаётся визуальным якорем.
- **Раньше:** возвратные масштаб и blur занимали всю длительность полёта и
  начинались одновременно с ним; для фона применялась отдельная
  cubic-bezier `[0.4, 0, 0.6, 1]`.

### Текст кейса во время входа

- **Сейчас:** видимые блоки проявляются за `360 ms`, когда spring обложки
  проходит `95%` пути. Заголовок одновременно раскрывается горизонтальной
  маской. Начальное значение зарегистрированной маски равно `100%`.
- **Почему:** пока обложка пересекает экран, взгляд остаётся на ней; текст
  появляется ближе к посадке. Порог берётся из progress той же spring-кривой,
  поэтому он не зависит от произвольной задержки. Значение `100%` не даёт
  заголовку повторно скрыться, когда анимация снимается при handoff.
- **Раньше:** фиксированная задержка `168 ms` запускала текст раньше желаемого,
  пока пользователь ещё следил за обложкой. Маска сбрасывалась к `0%`, из-за
  чего заголовок мог моргнуть после приземления.

### Вход карточек и переключение Birdview ↔ Snakeview

- **Сейчас:** карточки Motion spring `560 ms`, `opacity: 0 → 1`,
  `y: 18px → 0`; базовая задержка `220 ms`, шаг строк `90 ms`. About начинает
  с базовой строки, а первая строка кейсов использует следующий stagger и
  начинает через `310 ms`.
  Переключение видов использует Motion spring `320 ms` для масштаба, opacity и
  промежутка строк; завершение ждёт оба слоя.
- **Почему:** сохранили прежние темп, смещение, stagger и геометрию видов,
  поменяли форму затухания на spring без отскока. Состояние переключения теперь
  закрывается по завершению обеих анимаций, а не отдельным таймером.
- **Раньше:** вход карточек использовал cubic-bezier `[0.16, 1, 0.3, 1]`, а
  смена видов и layout — `[0.22, 1, 0.36, 1]`. Смена вида завершалась через
  `setTimeout(320 ms)`.

### Перевод `EN ↔ RU`

- **Сейчас:** текст crossfade'ится нативным Motion spring `180 ms`; сдвиг
  карточек после изменения длины текста использует Motion spring `240 ms`.
  Layout spring включается только на кадр локального reflow.
- **Почему:** текст и новая геометрия приходят согласованно, при этом layout
  spring не вмешивается в отдельное переключение Birdview ↔ Snakeview.
- **Раньше:** crossfade текста использовал `easeOut` за `180 ms`, layout —
  cubic-bezier `[0.22, 1, 0.36, 1]` за `240 ms`.

### About и Telegram CTA

- **Сейчас:** About раскрывается горизонтальной маской по фактическим строкам;
  длительность каждой строки зависит от её длины. CTA появляется через `250 ms`
  после измерения строк и проявляется за `350 ms` вместе со снятием blur.
  Оба эффекта используют общую CSS `linear()`-аппроксимацию spring.
- **Почему:** маска следует реальному переносу текста и избегает второй
  opacity-анимации. Фиксированная пауза CTA отделяет его появление от расчёта
  строк, число которых зависит от ширины экрана.
- **Раньше:** easing маски About был `[0.16, 1, 0.3, 1]`, easing CTA —
  `[0.12, 1, 0.2, 1]`; правила строк, stagger и задержки CTA были отдельными.

### Прокрутка наверх

- **Сейчас:** Motion spring `bounce: 0`, длительность ограничена `320–700 ms`
  и зависит от `scrollY`. Анимация отменяется при жесте или вводе с клавиатуры;
  `scroll-behavior` установлен в `auto`.
- **Почему:** прокруткой управляет одна отменяемая анимация, без конкурирующего
  браузерного smooth scroll.
- **Раньше:** собственный RAF вычислял quintic ease-out
  `1 - (1 - progress)^5`; глобальный CSS `scroll-behavior: smooth` мог добавить
  второй слой сглаживания.

### Следование курсора

- **Сейчас:** курсоры карточек, Telegram CTA и страницы 404 используют точный
  аналитический шаг критически затухающей пружины. Скорость переносится при
  каждой смене цели; координаты записываются прямо в DOM через RAF. Появление
  курсора 404 отдельно меняет opacity и scale по CSS spring-кривой.
- **Почему:** цель курсора меняется непрерывно, поэтому решение сохраняет
  скорость и даёт безотскочное следование без React-рендера на каждом кадре.
- **Раньше:** позиция двигалась на `25%` оставшегося расстояния за кадр; курсор
  404 дополнительно обновлял React state на каждом кадре. Такое сглаживание
  зависело от частоты кадров и не переносило скорость к новой цели.

### Короткие CSS-переходы

- **Сейчас:** цвета, opacity, ширина и размеры навигации, ссылки, кнопки,
  подписи, video poster и видимость курсора 404 используют
  `--spring-zero-bounce-easing`, то есть
  CSS `linear()`-аппроксимацию Motion spring `bounce: 0`. Длительность задаётся
  отдельно для каждого эффекта.
- **Почему:** мелкие hover/focus-состояния остаются короткими CSS-переходами;
  им не требуется перенос скорости при смене цели. Это форма кривой Motion,
  но не нативное выполнение Motion spring. Это не заявка на доказанное
  ускорение сайта: отдельный benchmark этих переходов не проводился.
- **Раньше:** использовались разные `cubic-bezier`, `ease-out` и `ease`, например
  `[0.22, 1, 0.36, 1]`, `[0.4, 0, 0.2, 1]` и `[0.16, 1, 0.3, 1]`.

## Главная

### Первое появление карточек

Обычные карточки появляются из `opacity: 0` и `y: 18px` с Motion spring
`duration: 560 ms`, `bounce: 0`. Первая строка стартует через `220 ms`, каждая
следующая — ещё через `90 ms`. Это правило не применяется к About в Snakeview.
Пока клиентский React не завершил hydration, `.view-stage[data-view-ready="false"]`
временно держит карточки видимыми; этот fallback не заменяет entrance-анимацию
после готовности клиента и нужен, чтобы задержка hydration не выглядела как
пустая главная.

### Переключение Birdview ↔ Snakeview

Обе раскладки на время перехода остаются в DOM. Они стартуют одновременно и
используют Motion spring `duration: 320 ms`, `bounce: 0`:

| Направление | Исходная раскладка | Входящая раскладка |
| --- | --- | --- |
| Birdview → Snakeview | `scale: 1 → 1.1`, `opacity: 1 → 0` | `scale: 0.9 → 1`, `opacity: 0 → 1` |
| Snakeview → Birdview | `scale: 1 → 0.9`, `opacity: 1 → 0` | `scale: 1.1 → 1`, `opacity: 0 → 1` |

Меняется и межстрочный ритм: Birdview `174px → 120px` при входе из Snakeview,
Snakeview `44px → 120px` при входе из Birdview. Названия направления в коде
всегда явные: `birdviewToSnakeview` и `snakeviewToBirdview`.

### About в Snakeview

Текст About раскрывается только горизонтальной маской, без смещения по `x` или
`y`. Строки определяются по фактическому переносу после layout. У каждой строки:

- маска идёт от `-16%` до `100%`, ширина мягкой границы — `16%`, с CSS-
  аппроксимацией spring `bounce: 0`;
- длительность зависит от длины строки: `clamp(240 ms, 144 ms + 6 ms × число
  символов, 480 ms)`;
- следующая строка стартует через `7%` длительности предыдущей.

Не добавлять к этим строкам отдельную opacity-анимацию: это создаёт видимое
двухэтапное появление и столбик начал строк.

Telegram-CTA получает отдельное появление после готовности измеренных строк
текста About с фиксированной задержкой `250 ms`, чтобы первый экран не зависел
от количества строк в конкретном viewport. CTA появляется из полной
прозрачности (`opacity: 0 → 1`) и с `filter: blur(12px) → blur(0)` за `350 ms`
с CSS spring `bounce: 0`. Настройка задержки находится в
`components/Portfolio.tsx` (`--hero-about-telegram-reveal-delay`), длительность
— в `styles.css` у `.hero-about__telegram`.

В Snakeview и Birdview первая строка карточек кейсов начинает появляться через
`310 ms`; межстрочный stagger `90 ms` сохраняется.

Поведение CTA после появления — отдельное: на desktop внутренняя зелёная карточка
плавно следует за курсором; на mobile и при reduced motion это выключено.

### Смена языка

Текст локали crossfade'ится с Motion spring `duration: 180 ms`, `bounce: 0`.
Layout-переход карточек при смене локали использует spring `duration: 240 ms`,
`bounce: 0`. Конфигурация spring включается на кадре локального reflow и не
включает layout-анимации при переключении Birdview ↔ Snakeview.

## Карточка ↔ обложка кейса

### Контракт и причина рефакторинга 2026-09-20

Сохраняется одна persistent-обложка: карточка переходит в реальную обложку
кейса, а возврат восстанавливает выбранный Birdview/Snakeview и scroll.
При глубоком scroll нет полёта через весь экран: родная карточка появляется
локальным движением `scale(1.08 → 1)`.

Старые независимые таймеры заменены одним жизненным циклом. Раньше возврат
отсчитывался до монтирования главной, а завершение открытия — до готовности
replacement image. Из-за этого подготовка страницы могла съедать время
видимой анимации. Кривая возврата на 250 ms проходила большую часть пути в
первые 50 ms; её замена одним увеличенным числом не устраняла эту проблему.

### Подготовка, движение, передача изображения

- `preflight`: сохраняются snapshot, исходная обложка и scroll. Начальная
  геометрия удерживается до появления реального destination DOM. Destination
  измеряется дважды после восстановления layout и scroll; приближённой
  геометрии по viewport нет. Главная заранее загружает маршруты четырёх
  доступных кейсов, включая карточки ниже первого экрана, чтобы ожидание
  destination DOM редко попадало между кликом и началом движения.
- `landing`: открытие использует spring `640 ms`, видимый возврат — `480 ms`,
  offscreen-return — `450 ms`; все с `bounce: 0`. Завершение определяется
  animation controls, не таймером. Синхронизация дочерних эффектов использует
  фактическую длительность geometry control: duration-based spring в `motion/mini`
  может округлить заданное время до ближайшего шага генератора `50 ms`.
- При открытии source-обложка начинает смешиваться с hero одновременно с
  полётом за `160 ms`. При видимом возврате case-обложка смешивается с homepage
  cover за `150 ms`, по центру участка, где spring проходит половину пути.
  Время берётся из той же Motion spring progress-кривой, а не из половины
  длительности: большая часть затухания приходится на финальное приближение.
  Поэтому карточный арт полностью виден до посадки. При разных пропорциях кейса
  и карточки меняется обрезка рамки, а содержимое компенсирует разницу масштаба,
  чтобы не растягиваться. Перед возвратом текущий видимый кадр обложки
  захватывается с его текущей обрезкой в bitmap, чтобы повторный mount
  изображения или видео не заменял первый кадр плейсхолдером.
  Замена декодируется параллельно движению, а оставшаяся задержка считается от
  стартового таймлайна, чтобы decode не запускал новый отсчёт.
- Движение фона и blur занимают `75%` фактической длительности geometry spring.
  При открытии они начинаются вместе с полётом; при возврате начинаются после
  первой четверти полёта и завершаются вместе с ним. В preflight canvas удерживает
  начальную opacity `0.33`, чтобы не мигнуть до старта общего таймлайна.
- Decode реальной обложки маршрута происходит параллельно с движением и нужен
  лишь перед передачей изображения. Медленная загрузка маршрута по-прежнему
  задерживает начало движения, поскольку его геометрия измеряется в настоящем
  DOM.
- При offscreen-return case-обложка уже не имеет видимой пространственной
  траектории. Persistent layer с первого кадра homepage использует только
  финальную source-обложку карточки; crossfade с case-обложкой в этот сценарий
  не входит.
- `handoff`: геометрия и crossfade завершены; реальная обложка становится
  видимой под persistent layer, затем после отрисованного кадра слой снимается.
- Recovery timeout служит только защитой от зависания. Он не задаёт длину
  нормального перехода. Ошибка ассета освобождает страницу через fade, а
  browser Back и уход на другой route отменяют старую сессию и её callbacks.

### Отрисовка

Главные transform/opacity выполняются через `motion/mini` и браузерный Web
Animations API. Этот путь не оставляет transient
transform в MotionValues компонентов React; canvas заканчивает на `transform:
none`, чтобы fixed-курсор карточки снова отсчитывался от viewport.
При возврате canvas одновременно масштабируется из `.94`, проявляется из `.33`
и снимает `blur(18px)` на spring `bounce: 0` в последние `75%` длительности
полёта.
Блоки контента кейса проявляются, когда Motion spring проходит `95%` пути
(для текущего полёта это около `329 ms` после старта), за `360 ms` из
прозрачности и `blur(12px)` без дополнительного вертикального сдвига; заголовок
за то же время дополнительно раскрывается горизонтальной маской на spring
`bounce: 0`. Зарегистрированное CSS-свойство маски начинает с `100%`, поэтому
снятие WAAPI-анимации на handoff не скрывает заголовок повторно.
Собственного покадрового RAF,
обновляющего наследуемые CSS variables на корне, больше нет. Геометрия
измеряется только до старта, `left/top/width/height` во время движения неизменны.

Главная остаётся единым полотном с мягким scale/opacity. При возврате на это
полотно кратковременно применяется фильтр blur, чтобы размытие читалось вместе
с уменьшением обложки, как в локальной версии. При открытии используется
фиксированная viewport-подложка; reveal текста работает только на видимых
блоках. Мобильную производительность возврата проверять отдельно: фильтр
длинного полотна дороже фиксированной подложки.

Target posters подготавливаются только для активной раскладки рядом с viewport,
с обычным приоритетом и `sizes` реального hero. Невидимые видео кейса не
начинают загрузку и autoplay вместе с открытием страницы. `prefers-reduced-motion`
сохраняет обычную навигацию без shared-cover эффекта.

## Проверка после изменения motion

1. Проверить первый кадр: контент не должен мигать или появляться дважды.
2. Проверить оба направления Birdview ↔ Snakeview и `EN ↔ RU`.
3. Проверить вход и возврат из кейса в обоих видах, включая возврат после
   глубокой прокрутки.
4. Проверить desktop, mobile и `prefers-reduced-motion`.
5. Выполнить `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` и
   `git diff --check` в зависимости от затронутого кода.
6. Задержать загрузку и decode hero: геометрия должна завершиться независимо,
   а handoff — дождаться изображения. Ошибка медиа и recovery должны освободить
   scroll; поздний callback отменённого перехода не влияет на следующий кейс.
7. После обычного или прерванного возврата проверить `transform: none` у
   homepage canvas и совпадение fixed-подписи карточки с положением курсора.
   Даже identity transform создаёт содержащий блок и может сместить подпись.
